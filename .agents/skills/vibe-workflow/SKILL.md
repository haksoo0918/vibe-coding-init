# 바이브 코딩 워크플로우 스킬 (Vibe Coding Workflow Skill)

본 스킬은 **메인 에이전트(오케스트레이터)가** 사용자와 함께 '바이브 코딩'을 진행할 때, 프로젝트의 방향성을 통제하고 **서브 에이전트(워커)에게** 안전하게 작업을 위임하여 개발을 완수하도록 돕는 가이드라인입니다.

---

## 1. 활성화 시점 (When to use)
- 사용자가 새로운 기능을 요청하거나 아키텍처/스펙 변경을 지시했을 때
- 복수의 구현 방식이 존재하여 2~3가지 작업 방향 제시가 필요할 때
- PRD 작성 및 사용자 승인 후 서브 에이전트를 호출하여 작업을 위임할 때
- 대규모 협업을 위해 `/teamwork` 모드를 제안하고 팀을 구성할 때
- **사용자가 명시적으로 `main` 머지, 배포, 또는 GitHub 푸시를 요청했을 때**

---

## 2. 메인/서브 에이전트 표준 실행 흐름

```text
[1단계: 요청 분석 & 방향 제시] (메인 에이전트)
       │ (2~3가지 접근법 및 트레이드오프 제안)
       ▼
[2단계: PRD 작성 및 업데이트] (메인 에이전트: ./PRD.md)
       │
       ▼
[3단계: 사용자 승인 확인] (메인 에이전트: 승인 전 코드 수정 및 서브에이전트 호출 금지)
       │ (승인 완료)
       ▼
[4단계: 서브 에이전트 위임 TDD 구현 & 검증]
       ├─ 메인 에이전트: 작업 분할 ➔ 서브 에이전트 호출 (invoke_subagent 또는 /teamwork)
       ├─ 서브 에이전트: tdd 스킬 준수 (Red-Green 루프) ➔ Lint 실행 ➔ 완료 보고
       └─ 메인 에이전트: 산출물 검토 ➔ dev 브랜치 자율 커밋 (dev 브랜치 상태 유지)
       │
       │ (★ 오직 사용자가 명시적으로 머지/배포/푸시를 요청했을 때만 실행!)
       ▼
[5단계: 사용자 요청 시 ➔ CHANGELOG.md 업데이트, main 머지 및 GitHub 푸시] (메인 에이전트)
```

### 1단계: 분석 및 다양한 작업 방향 제시 (메인 에이전트)
- 사용자 요청을 분류(신규 기능, 버그 수정, 사양 변경 등)합니다.
- 복수의 구현 방식이 존재하는 경우, **2~3가지 작업 방향(대안)과 장단점(트레이드오프)을** 사용자에게 먼저 제시하여 최선의 방향을 선택하도록 돕습니다.

### 2단계: PRD 작성 및 업데이트 (`./PRD.md`, 메인 에이전트)
- 사양이나 구조 변경 시 반드시 `./PRD.md`를 먼저 업데이트합니다.
- 서브 에이전트에게 할당할 단위 작업과 공개 인터페이스(Seam) 계획을 명시합니다.

### 3단계: 사용자 승인 요청 (메인 에이전트)
- PRD의 요약과 구현 계획을 사용자에게 전달하고 승인을 요청합니다:
  > "위 계획대로 진행해도 될까요? 승인해 주시면 서브 에이전트를 호출하여 구현을 시작합니다."
- 사용자가 동의하기 전까지는 **메인 에이전트는 물론 서브 에이전트도 실행하지 않습니다.**

### 4단계: 서브 에이전트 위임 TDD 구현 & 검증 (메인 & 서브 에이전트)
- **메인 에이전트**:
  - `invoke_subagent` 도구를 사용하여 서브 에이전트에게 작업을 위임합니다.
  - 대규모 작업의 경우 `/teamwork` 명령어를 활용합니다.
  - **메인 에이전트는 소스 코드를 직접 수정하지 않습니다.**
- **서브 에이전트**:
  - **TDD 기본 준수 ([tdd 스킬](../tdd/SKILL.md))**: Seam 식별 ➔ 실패하는 테스트(**Red**) ➔ 통과하는 최소 구현(**Green**)을 한 번에 한 슬라이스씩 진행.
  - **언어별 Lint 검증**: 지원되는 린터(ESLint, Biome, Stylelint, Ruff 등)를 실행하여 모든 오류를 해결.
  - 작업 결과를 메인 에이전트에게 명확히 보고.
- **메인 에이전트의 검토 및 커밋**:
  - 서브 에이전트의 보고 내용을 확인하고 이상이 없으면 한글 커밋 태그([rules/git-workflow.md](../../../rules/git-workflow.md))에 맞춰 **`dev` 브랜치에 자율 커밋하고**, **`dev` 상태를 유지합니다.**

### 5단계: 사용자 요청 시 ➔ CHANGELOG 작성, `main` 머지 및 GitHub 푸시 (메인 에이전트)
- 사용자가 "main에 머지해줘", "푸시해줘" 등 명시적으로 요청한 경우에만 실행합니다:
  1. `CHANGELOG.md`에 새 버전 번호, 날짜, 변경 내역을 작성/커밋합니다.
  2. `main` 브랜치로 전환 후 `dev` 브랜치를 머지합니다.
  3. 원격 저장소가 등록되어 있으면 `git push origin main` 및 `git push origin dev`를 실행합니다.
  4. 완료 후 다시 `dev` 브랜치로 체크아웃하여 다음 작업을 준비합니다.
