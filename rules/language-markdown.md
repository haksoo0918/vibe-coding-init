# 언어 및 마크다운 작성 규칙 (Language & Markdown Guide)

본 문서는 프로젝트 내에서 작성되는 모든 문서, 대화 응답, 코드 주석 및 산출물의 언어 사용과 마크다운 서식에 대한 기준을 정의합니다.

---

## 1. 언어 원칙 (Language Policy)

1. **기본 원칙**: 모든 사용자 응답, 프로젝트 문서, 코드 주석, 커밋 메시지는 **한국어**로 작성합니다.
2. **기술 용어 표기**:
   - 널리 통용되는 기술 용어는 자연스러운 한글 표기를 우선합니다 (예: 빌드, 배포, 컴포넌트, 핸들러, 브랜치).
   - 의미 혼동을 방지해야 하거나 원문 명칭이 중요한 경우 **한글(영문 병기)** 형태로 작성합니다.
     - 예: 상태 관리(State Management), 의존성 주입(Dependency Injection), 비동기 처리(Asynchronous Processing)
   - 코드 식별자(함수명, 변수명, 클래스명, 파일 경로 등)는 원문 코드 그대로 백틱(`)으로 감싸 표기합니다.
3. **톤앤매너**:
   - 정중하고 명확하며, 불필요한 수식어를 줄인 실용적인 어조(하십시오/해요체)를 사용합니다.
   - 문서는 개조식과 서술식을 적절히 조합하여 가독성을 극대화합니다.

## 2. 한글 마크다운 서식 오류 주의사항 (`**`, `~`, `` ` ``)

마크다운 파서(CommonMark, GitHub Flavored Markdown 등)는 한국어와 인라인 서식 기호가 결합될 때 단어 경계(Word Boundary)를 영어와 다르게 인식하여 **서식이 깨지거나 기호가 그대로 노출되는 오류**가 자주 발생합니다. 다음 규칙을 반드시 준수합니다.

### 2.1 굵은 글씨 (`**`) 서식 깨짐 방지
- **문제점**: 닫는 `**` 기호 바로 뒤에 한글 조사(`은/는/이/가/을/를/의/에/로` 등)가 공백 없이 붙으면 파서가 굵은 글씨를 인식하지 못하고 `**텍스트**가` 형태로 그대로 출력될 수 있습니다.
- **해결 원칙**:
  1. **조사까지 강조에 포함**: 가능하면 조사까지 강조 영역 안에 함께 넣습니다.
     - 올바른 예: `**해당 파일은** 수정하지 않습니다.`
  2. **공백 분리 또는 문맥 재배치**: 조사를 분리하거나 문맥을 다듬어 기호 뒤에 조사가 바로 붙지 않도록 합니다.
     - 올바른 예: `다음 항목인 **[설정 파일]** 을 확인합니다.`

### 2.2 취소선 (`~`, `~~`) 사용 주의
- **문제점**: 물결표(`~` 또는 `~~`)는 마크다운 렌더러에 따라 1개(`~text~`)만 지원하거나 2개(`~~text~~`)를 요구하며, 한글 음절 앞뒤로 공백이 없으면 취소선이 적용되지 않고 물결표가 노출됩니다.
- **해결 원칙**:
  - 취소선은 표준인 쌍물결표(`~~...~~`)를 사용합니다.
  - 서식 기호 앞뒤에 띄어쓰기를 명확히 두거나 조사 결합을 피합니다.
  - 예: `기존 방식인 ~~레거시 인증~~ 대신 신규 토큰 방식을 사용합니다.`

### 2.3 인라인 코드 (`` `...` ``) 및 괄호 활용
- 인라인 코드 뒤에 조사가 붙는 경우 가독성과 파싱 안정성을 위해 작은 괄호나 공백을 고려합니다.
  - 권장: `` `dev` 브랜치 ``, `` `CHANGELOG.md` 파일 ``

## 3. 코드 주석 규칙 (Source Comments)

1. **주석 작성 언어**: 소스 코드 내 작성되는 주석(JSDoc, Docstring, 인라인 주석)은 **한국어**로 작성합니다.
2. **기존 주석 보존**: 작업 대상과 직접적인 관련이 없는 기존 주석이나 문서화 내용은 임의로 삭제하거나 왜곡하지 않고 그대로 유지합니다.
3. **주석 작성 기준**:
   - 코드 자체로 명확한 단순 동작은 주석을 남발하지 않습니다.
   - 복잡한 비즈니스 로직, 예외 처리 이유, 성능 고려 사항 등 **'왜(Why)'** 이렇게 작성되었는지를 설명합니다.

 * @returns 갱신된 세션 정보 또는 만료 시 null
 */
export async function validateOrRefreshToken(token: string): Promise<Session | null> {
  // 토큰 만료 5분 전 미리 갱신하여 네트워크 지연으로 인한 세션 끊김 방지

## 4. 마크다운 작성 서식 (Markdown Formatting)

1. **제목 구조 (Headings)**:
   - 문서당 최상위 제목(`#`)은 1개만 사용합니다.
   - 계층 순서(`#` ➔ `##` ➔ `###`)를 건너뛰지 않습니다.
2. **목록 및 들여쓰기**:
   - 순서가 없는 목록은 `-` 기호를 일관되게 사용합니다.
   - 하위 항목은 공백 2칸 또는 4칸으로 일관되게 들여씁니다.
3. **코드 블록 (Fenced Code Blocks)**:
   - 코드 블록 작성 시 반드시 언어 식별자(예: `bash`, `typescript`, `python`, `json`, `yaml`, `css`)를 명시합니다.
   - 파일 경로나 단일 식별자는 인라인 백틱(`...`)으로 감쌉니다.
4. **강조 및 인용구**:
   - 중요한 요구사항이나 주의점은 볼드체 또는 GitHub 스타일 알림(Alerts) 블록을 활용합니다.
   ```markdown
   > [!NOTE] 배경 설명이나 부가 정보를 작성합니다.
   > [!IMPORTANT] 반드시 준수해야 하는 핵심 요구사항입니다.
   > [!WARNING] 호환성 문제나 주의가 필요한 사항입니다.
   ```
5. **링크 표기**:
   - 파일 경로는 상대 경로를 활용한 마크다운 링크로 작성하여 쉽게 탐색할 수 있도록 합니다. 링크 텍스트는 프로젝트 루트 기준 경로로 명시합니다.
     - 예: `[rules/agent-execution.md](agent-execution.md)`
