# 코드 품질 및 개발 원칙 (Code Quality & Development Principles)

본 문서는 프로젝트 소스 코드의 가독성, 유지보수성, 안정성을 보장하기 위한 코딩 원칙, 테스트 주도 개발(TDD) 수칙, 린트(Lint) 검증 기준을 정의합니다.

---

## 1. 테스트 주도 개발 (TDD) 기본 원칙

본 프로젝트의 모든 신규 기능 구현 및 버그 수정은 **[.agents/skills/tdd](../.agents/skills/tdd/SKILL.md) 스킬에 기반한 TDD를 기본 개발 표준**으로 적용합니다.

### 1.1 Red ➔ Green 개발 루프
1. **Red (실패하는 테스트 우선 작성)**:
   - 구현 코드를 작성하기 전에 기대되는 동작을 명시한 테스트를 먼저 작성합니다.
   - 테스트 실행 시 기대한 이유로 실패하는지 확인합니다.
2. **Green (최소한의 구현 작성)**:
   - 실패한 테스트를 통과시키는 데 꼭 필요한 최소한의 코드만 작성합니다. 미래의 요구사항을 넘겨짚어 불필요한 코드를 미리 작성하지 않습니다.
3. **수직 슬라이싱 (Vertical Slicing)**:
   - 한 번에 모든 테스트를 대량으로 먼저 작성하고 한꺼번에 구현하는 수평적 슬라이싱을 금지합니다.
   - 하나의 Seam(접합부) ➔ 하나의 테스트(Red) ➔ 하나의 최소 구현(Green)을 점진적으로 반복합니다.

### 1.2 접합부 (Seam) 중심 테스트
- **테스트 위치**: 내부 구현 세부사항(Private 메서드, 내부 상태)이 아닌, 외부에서 관찰 가능한 **공개 인터페이스(Seam)**를 검증합니다.
- **장점**: 내부 코드가 완전히 리팩토링되어도 공개 인터페이스 동작이 바뀌지 않는 한 테스트가 깨지지 않고 유지됩니다.

### 1.3 피해야 할 안티패턴 (Anti-patterns)
- **구현 결합(Implementation-coupled)**: 내부 비공개 함수를 모킹하거나 테스트하여, 리팩토링 시 기능은 정상인데 테스트만 깨지는 현상.
- **동어반복(Tautological)**: 구현 코드의 계산식을 테스트에서 그대로 다시 계산하여 항상 참이 되게 만드는 무의미한 단언(`expect(add(a, b)).toBe(a + b)` 등). 기댓값은 명세나 독립된 출처로부터 얻어야 합니다.
- **모의 객체(Mock) 남발**: 실제 객체로 테스트 가능한 경계까지 과도하게 모킹하는 것을 지양하고, 시스템 외부 경계(네트워크, 외부 API, 시간 등)에만 제한적으로 모킹을 사용합니다 ([.agents/skills/tdd/mocking.md](../.agents/skills/tdd/mocking.md) 참조).

## 2. 언어별 린터(Linter) 및 포매터 필수 적용

프로젝트 언어 및 개발 환경마다 지원되는 정적 분석/린트(Lint) 도구가 있는 경우, **코드 작성 및 수정 후 반드시 린트를 실행하여 모든 오류와 경고를 해결한 뒤 작업을 완료**해야 합니다.

### 권장 린트/포매팅 도구 기준

| 언어 / 환경 | 권장 린터 및 포매터 | 필수 검증 명령 예시 |
| :--- | :--- | :--- |
| **JavaScript / TypeScript** | ESLint, Biome, Prettier | `npm run lint` / `pnpm lint` / `npx eslint .` |
| **Python** | Ruff, Flake8, Black, mypy | `ruff check .` / `flake8` / `mypy .` |
| **CSS / SCSS** | Stylelint | `npx stylelint "**/*.css"` |
| **HTML / 마크다운** | markdownlint | `npx markdownlint-cli "**/*.md"` |
| **Go** | golangci-lint, go vet | `golangci-lint run` / `go vet ./...` |
| **Rust** | clippy, rustfmt | `cargo clippy` / `cargo fmt --check` |

> [!IMPORTANT]
> 프로젝트에 이미 설정된 린트 스크립트(예: `npm run lint`, `pnpm run check`)가 있다면 해당 명령을 우선 실행하며, 규칙을 무시하는 인라인 주석(`eslint-disable`, `# noqa` 등)의 남발을 금지합니다.

## 3. 스타일 가이드 준수

1. **CSS 스타일**:
   - 웹 및 UI 스타일시트 작성 시 [rules/css-style-guide.md](css-style-guide.md)에 정의된 모던 CSS 아키텍처(`@layer`, `:root` 토큰, 네이티브 네스팅, 모던 가상 클래스, `clamp()` 유체 디자인)를 엄격히 준수합니다.
2. **코드 스타일 일관성**:
   - 기존 코드베이스의 들여쓰기(2칸 vs 4칸), 따옴표(Single vs Double), 세미콜론 규칙을 임의로 변경하지 않고 일관되게 따릅니다.

## 4. 핵심 설계 원칙

1. **단순성 유지 (KISS - Keep It Simple, Stupid)**:
   - 과도한 추상화나 불필요하게 복잡한 디자인 패턴을 지양하고, 읽기 쉽고 직관적인 코드를 작성합니다.
2. **필요할 때 구현 (YAGNI - You Aren't Gonna Need It)**:
   - 현재 요구사항에 정의되지 않은 막연한 미래의 기능을 미리 예측하여 구현하지 않습니다.
3. **단일 책임 원칙 (Single Responsibility)**:
   - 함수나 모듈은 한 가지 명확한 역할에 집중하도록 작성하며, 함수 길이가 지나치게 길어지지 않도록 적절히 분리합니다.

---

## 5. 에러 핸들링 및 로깅

1. **에러 삼키기 금지 (No Silent Failures)**:
   - 빈 `catch` 블록이나 에러를 무시하는 처리를 지양합니다.
   - 예외 발생 시 원인을 파악할 수 있는 유의미한 에러 메시지와 함께 로깅하거나 상위 호출자에게 적절히 전파합니다.
2. **사용자 친화적인 메시지**:
   - 클라이언트/사용자에게 노출되는 에러 메시지는 시스템 내부 스택 트레이스를 숨기고, 사용자가 취할 수 있는 조치를 명확히 안내합니다.
3. **상세 디버그 로그**:
   - 디버깅이 필요한 핵심 분기점에는 주요 상태 값과 함께 명확한 로그를 남깁니다.
