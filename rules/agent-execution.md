# 에이전트 실행 프로토콜 (Agent Execution Protocol)

본 문서는 프로젝트 내에서 작업을 수행하는 **메인 에이전트(오케스트레이터)**와 **서브 에이전트(워커)**의 분리된 행동 규칙, 위임 프롬프트 규격 및 실행 절차를 정의합니다.

---

## 1. 메인-서브 에이전트 분리 기본 원칙

```text
[ 사용자 ]
    ▲
    │ (대화, 요구사항 전달, 승인)
    ▼
[ 메인 에이전트 (오케스트레이터) ] ◄── 직접 코드 수정 절대 금지!
    │ (기획, PRD 관리, 방향 제시, 작업 분할)
    │
    ▼ (invoke_subagent / /teamwork 호출)
[ 서브 에이전트 (워커) ] ◄────────── TDD(Red-Green) 실제 구현, Lint 검증 전담
```

1. **메인 에이전트의 코드 직접 수정 금지**:
   - 메인 에이전트는 기획, 아키텍처 수립, 작업 분할, 서브 에이전트 관리 및 최종 검토만 수행합니다.
   - 실제 소스 코드 파일(`.ts`, `.js`, `.py`, `.css` 등)이나 테스트 코드를 직접 생성하거나 수정하지 않습니다.
2. **사전 분석 및 대안 제시**:
   - 메인 에이전트는 본격적인 기획 전, 해결 방법이 여러 가지인 경우 **2~3가지의 작업 방향(대안)과 장단점(트레이드오프)**을 사용자에게 먼저 제시합니다.
3. **PRD 우선 갱신 및 승인 원칙**:
   - 동작이나 사양 변경이 필요한 경우 메인 에이전트가 `PRD.md`를 작성/갱신하고 사용자의 **명시적 승인**을 받습니다.
4. **서브 에이전트 위임 및 TDD 필수**:
   - 사용자 승인 완료 후, 메인 에이전트는 [제3장 서브 에이전트 위임 템플릿](#3-서브-에이전트-위임-표준-프롬프트-템플릿) 규격에 맞춰 서브 에이전트를 호출(`invoke_subagent`)합니다.
   - 서브 에이전트는 **[.agents/skills/tdd](../.agents/skills/tdd/SKILL.md)** 스킬을 필수로 준수하여 **실패하는 테스트 작성(Red) ➔ 통과하는 최소 구현(Green)**을 수행합니다.
5. **언어별 Lint 검증**:
   - 서브 에이전트는 구현 완료 후 해당 언어의 린터(Linter)를 실행하여 모든 오류와 경고를 해결한 뒤 결과를 보고합니다.
6. **대규모 협업 시 `/teamwork` 활용**:
   - 대규모 기능이나 프론트엔드/백엔드/인프라 병렬 작업이 필요한 경우, 사용자에게 `/teamwork` 명령어 사용을 권장하여 전문 에이전트 팀을 구성합니다.
7. **`dev` 브랜치 유지 및 사용자 요청 기반 머지/푸시**:
   - 모든 일상 개발은 `dev` 브랜치에 머무르며 진행하고 자율 커밋합니다.
   - **`main` 브랜치 머지, `CHANGELOG.md` 작성 및 원격 저장소(GitHub 등) 푸시는 에이전트가 임의로 하지 않고, 오직 사용자의 명시적 요청 시에만 수행합니다** ([rules/git-workflow.md](git-workflow.md) 준수).

## 2. 작업 단계별 세부 실행 절차

### 1단계: 요청 분석 및 작업 방향 제시 (메인 에이전트)
- 사용자 요청을 분류(신규 기능, 버그 수정, 사양 변경 등)합니다.
- 복수의 구현 방식이 존재할 경우, 최소 2가지 이상의 대안과 장단점(복잡도, 유지보수성, 성능)을 요약하여 제시하고 사용자와 협의합니다.

### 2단계: PRD 작성 및 갱신 (메인 에이전트)
- 협의된 방향을 바탕으로 `PRD.md`에 배경, 요구사항, 공개 인터페이스(Seam) 계획, 서브 에이전트 작업 분할 계획을 기록합니다.

### 3단계: 사용자 승인 대기 (메인 에이전트)
- 작성된 PRD 내용을 사용자에게 공유하고 승인을 확인합니다.
- **사용자의 승인이 떨어지기 전까지는 서브 에이전트를 호출하지 않습니다.**

### 4단계: 서브 에이전트 위임 TDD 구현 & Lint 검증 (메인 & 서브 에이전트)
1. **메인 에이전트**:
   - 승인된 작업을 단위별로 분할하여 아래 [제3장 위임 템플릿](#3-서브-에이전트-위임-표준-프롬프트-템플릿) 규격에 따라 서브 에이전트를 호출합니다 (`invoke_subagent` 도구 사용).
   - 대규모 작업의 경우 `/teamwork` 모드를 활용합니다.
2. **서브 에이전트**:
   - 전달받은 명세에 따라 실패하는 테스트 코드(Red)를 먼저 작성합니다.
   - 테스트를 통과시키는 최소한의 구현 코드(Green)를 작성합니다.
   - 린트(Lint) 도구를 실행하여 오류가 없음을 검증하고 메인 에이전트에게 보고합니다.
3. **메인 에이전트의 검토 및 자율 커밋**:
   - 서브 에이전트의 보고와 산출물을 검토합니다.
   - 기준을 통과하면 `dev` 브랜치에 한글 커밋 태그 컨벤션([rules/git-workflow.md](git-workflow.md))에 맞춰 커밋을 기록하고, **`dev` 브랜치 상태를 유지**합니다.

### 5단계: 사용자 요청 시 ➔ CHANGELOG 작성, `main` 머지 및 GitHub 푸시 (메인 에이전트)
- **오직 사용자가 명시적으로 머지 또는 배포/푸시를 요청했을 때만 실행합니다.**
- 메인 에이전트가 다음 절차를 차례대로 완수합니다:
  1. `CHANGELOG.md`에 신규 버전 번호, 날짜, 변경 내역을 작성/커밋합니다.
  2. `main` 브랜치로 전환 후 `dev` 브랜치를 머지합니다.
  3. 원격 Git 저장소(GitHub 등)가 연결되어 있는 경우, `git push origin main` 및 `git push origin dev`를 실행합니다.
  4. 머지 및 푸시 완료 후 다시 `dev` 브랜치로 체크아웃하여 대기합니다.

## 3. 서브 에이전트 위임 표준 프롬프트 템플릿

메인 에이전트가 `invoke_subagent` 도구를 호출할 때는 아래 템플릿 구조를 준수하여 서브 에이전트에게 전달합니다:

```markdown
[역할 정의]
당신은 본 프로젝트의 구현 전담 서브 에이전트(워커)입니다.
[.agents/skills/tdd/SKILL.md] 스킬을 준수하여 TDD 기반으로 개발을 수행하세요.

[작업 목표 및 범위]
- 대상 기능: [구현할 기능 또는 버그 수정 내용 명시]
- 관련 문서: [PRD.md 섹션 또는 관련 참조 문서 명시]
- 수정/생성 파일: [대상 파일 경로 명시]

[TDD 구현 및 검증 지침]
1. Seam 식별: 내부 구현이 아닌 공개 인터페이스의 동작을 검증하세요.
2. Red: 실패하는 테스트 코드를 먼저 작성하고 실패를 확인하세요.
3. Green: 테스트를 통과하는 최소한의 구현 코드만 작성하세요.
4. Lint 검증: 해당 언어의 린터(예: npm run lint, ruff check 등)를 실행하여 모든 경고와 오류를 해결하세요.
5. 언어 원칙: 코드 주석 및 커밋 메시지는 모두 한국어로 작성하세요 ([rules/language-markdown.md]).

[완료 보고 형식]
작업 완료 후 다음 항목을 포함하여 메인 에이전트에게 보고하세요:
1. 구현 요약
2. 생성/수정된 파일 목록
3. 테스트 통과 결과 및 실행 명령어
4. Lint 검증 통과 결과
```
